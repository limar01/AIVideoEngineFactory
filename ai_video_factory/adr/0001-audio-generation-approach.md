# ADR-0001: Audio/Narration Generation Approach

- **Date:** 2026-09-22
- **Status:** Accepted
- **Deciders:** User (via Personal Agent), Architecture Agent
- **Related:** Master Spec §10 (pipeline), §23 (narration style), §9 (shared stack)

---

## Context

The Master Spec pipeline (§10) has no explicit audio/narration step, yet:
- §23 defines "narration style" per template (Horror, Comedy, etc.)
- §22 mentions "audio mixing" in FFmpeg
- A 10-minute video is fundamentally audio-driven: narration timing dictates scene count and duration division (spec §1: 600s / 8s clips = 75 generation units, but this must be derived from narration pacing, not arithmetic alone)

The architecture must support an audio adapter (ARCHITECTURE.md §5.2) but the specific approach needs user resolution.

## Decision

**Local TTS via Piper** as the default audio provider, with `SilentTrackProvider` fallback.

- Default implementation: `PiperLocalProvider` — uses a locally-installed Piper binary with pre-downloaded `.onnx` model files
- Fallback for headless/degraded environments: `SilentTrackProvider` — produces a muted track matching scene duration so assembly can proceed end-to-end
- Adapter interface: `AudioProvider` with `synthesize(scene, text, voice) → TrackPath` and `available_voices() → list`
- Voice selection: per-niche voice profiles in `config/audio.yaml` (e.g., horror → "ryan_downs_amazon_neural_en-US" for narration, or Piper equivalent)
- Narration text: generated by the Story Engine (ADR-0002) alongside each scene; stored in `Scene.narration_text`
- Narration timing: `Scene.narration_seconds` is set from the synthesized audio duration and used to derive scene boundaries

## Consequences

### Positive
- **Free-tier**: no API costs for narration quota; Piper models are local
- **Private**: no data egress to cloud TTS providers
- **Reliable**: no network dependency during the generation pipeline
- **Fast**: local inference has no rate limits or latency beyond model load

### Negative
- **Voice quality**: local Piper voices are good but not as polished as premium cloud TTS (ElevenLabs, OpenAI)
- **Setup friction**: requires Piper binary + model download as a setup step
- **Voice variety**: limited voice selection compared to API providers

### Neutral
- Adapter pattern means switching to a cloud TTS provider (ElevenLabsProvider, OpenAITTSProvider) is a config change + credential swap — no pipeline changes needed

## Alternatives Considered

1. **ElevenLabs API:** Higher voice quality, but consumes quota, requires API key, and introduces a paid dependency. Rejected for v1 MVP.
2. **OpenAI TTS API:** Good quality and fast, but same quota/API-key concerns. Rejected for v1.
3. **User-supplied audio:** Requires user to produce/studio narration — too high-friction for automated pipeline. Rejected.

## Notes

The architecture is intentionally agnostic: `app/assembly/audio.py` defines the `AudioProvider` ABC. The active provider is selected via `config/audio.yaml::provider`. Switching requires only a config change and (if needed) credential setup — no code changes to the FFmpeg assembly layer.
